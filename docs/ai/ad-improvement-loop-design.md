### 1-2. 예상 이익 계산 범위 [확인]

`sales-core.js` 기준:

상품 판매금액(쿠폰 · 할인 반영, 취소 · 반품 제외, 결제금액이 맞지 않는 주문은 주문 당시 판매가로 추정) + 고객이 낸 배송비
− 적립금 사용 − 상품 원가 − 판매 수수료 − PG 수수료 − 배송비 수수료 − 택배 · 포장 · 기타 비용(설정값, 주문당 1회 최대값)
− Meta 광고비 전체(원화 환산)

- 비용을 저장한 상품만 계산하고, 미입력 상품의 판매는 빼되 광고비는 전체를 빼서 “일부 상품 기준”으로 표시.
- 반영하지 않음: 세금(부가세 등) · 인건비 · 임대료 · 고정비 · 반품 배송비.
- 광고별 손익분기는 광고 세트에 연결한 상품 1개의 마진 기준 참고값이며, 연결 마진이 최근 저장값과 다르면 판단 보류.

| 메인 사이트 영향 | 메인 사이트 화면은 `ad_log`의 모든 기록을 한 줄씩 표시 → 광고비 없는 새 종류 기록을 넣으면 **‘₩NaN’** 줄이 생김(기존 코드로 테스트해 확인, 5-6) |
| 현재 데이터 | 운영 DB 전체 `ad_log` 기록 0건(2026-10-06 읽기 전용 집계) |

## 3. 화면 · DB · 서버 변경 목록 [제안]

### 3-1. DB

| 변경 | 내용 | 원격 작업 |
|---|---|---|
| `ad_log` 기록 종류 추가 | `source:'change'`(실행 기록) · `source:'change_result'`(결과) — 같은 `tool_records` · 같은 tool_type. 수정 권한이 없으므로 결과 · 메모는 **새 기록으로 덧붙이고** `action_id`로 묶는다(이력 보존) | 없음(스키마 변경 없음). 단 메인 사이트 화면 보완이 먼저 배포돼야 함(5-4) |
| 사업 정보 | `tool_records` tool_type `business_profile`(쇼핑몰별, 최신 1건 사용 · 이전 기록 보존) | 없음 |
| 실행 기록 검색 성능 | `ad_log` 중 `source='change'` · `data->>'ad_id'` 부분 인덱스 | 필요 시(기록 수가 많아질 때) |
| 결과 판정 저장 | `ai_weekly_reviews.result`에 `action_reviews` 추가(jsonb 안) | 없음 |

### 3-2. 서버(`ai-weekly-review`)

1. 지시문 교체: policy MD 압축본 + `policy_version` · `playbook_version`을 결과에 기록.
2. 사례 선택: 판정 후보 · 전환 단계 · 소재 형식 · 사용자 자료 유무로 사례 유형을 서버에서 골라 1~2개만 전달(6장).
3. 사업 정보 입력 추가(4장), 없으면 “먼저 확인할 정보”로 질문.
4. 실행 기록 결과 확인: 열린 실행 기록(시작일 이후 비교 기간이 끝난 것)을 먼저 모아 광고별 지표를 같은 길이 기간으로 조회하고, 출력에 `action_reviews`를 받는다(5-3).
5. 출력 검증 확장: 판정 4종, `action_reviews` 근거 경로 검증, 예산 제안은 3장 조건 충족 여부를 서버가 함께 확인.

### 3-3. 화면

| 위치 | 변경 |
|---|---|
| 광고 카드 · 광고 개선안 | ‘실행 기록’ 버튼 → 변경 내용 확인 시트(AI 제안이 미리 채워짐, 사용자가 실제 변경으로 수정) |

## 5. AI 개선안 → 기존 광고 기록 연결 [제안]

### 5-1. 흐름

1. 광고 개선안(또는 유지 광고의 선택적 개선안)에서 ‘실행 기록’ 선택
2. 확인 시트: AI 제안이 미리 채워지고, 사용자가 **실제로 바꾼 것**으로 고친다(제안과 다르게 실행해도 사실대로)
3. 저장 → `ad_log`에 `source:'change'` 기록 1건 추가 → 광고 기록 표에 ‘변경’ 줄로 표시
4. 비교 기간이 끝나면 다음 주간 점검이 결과를 먼저 판정 → `change_result` 기록 추가 + 주간 결과의 `action_reviews`
5. 사용자는 결과에 메모를 덧붙일 수 있다(새 `change_result` 기록 · 기존 기록 수정 없음)

광고를 직접 바꾸는 기능은 포함하지 않는다(Meta 광고 수정 API 사용 안 함).

### 5-2. 기록 내용 (`ad_log`, `source:'change'`)

| 필드 | 내용 |
|---|---|
| `action_id` | 실행 기록 ID(결과 기록이 참조) |
| `store_id` · `date`(시작일) · `name`(사람이 읽는 제목) · `channel:'메타'` | 기존 광고 기록 표와 호환(`spend` · `revenue`는 넣지 않음) |
| `ad_id` · `adset_id` · `ad_name` | 대상 광고 |
| `suggestion` | 연결된 AI 제안: 주간 결과 ID · 주차 · 판정 · 바꿀 요소 · 수정 예시 · 정책/사례 버전 |
| `change` | 실제 변경 요소(문구 · 이미지 · 영상 첫 장면 · 타깃 · 예산 · 랜딩 · 기타) · 변경 내용(전/후 텍스트) · 방식(새 광고 추가 / 기존 광고 수정) · 새 광고 ID(있으면) |
| `compare` | 비교 기간(변경 전 n일 · 변경 후 n일, 같은 길이) · 비교 지표 · 판단 기준 |
| `baseline` | 변경 전 기준값(지표 값과 측정 상태) + 당시 계산 기준(귀속 설정 · 통화 · 환율 · 상품 계산 범위 · 연결 마진 버전 · 이익 공식 버전) |
| `creative_snapshot` | 당시 소재 문구 · 버튼 · 형식 · 게재 위치 요약 · 이미지 주소(만료 가능 표시). 이미지 파일 보관은 별도 결정(9장) |
| `concurrent` | 함께 바뀐 조건: 예산 · 할인 · 상품 · 타깃 · 게재 위치 · 기타(사용자 체크) |
| `memo` | 사용자 메모 |

`change_result`: `action_id` · 측정 시각 · 변경 후 값(측정 상태 포함) · 판정(개선 / 악화 / 차이 작음 / 판단 불가) · 판정 이유 · 비교 조건 경고 · 사용자 메모.

### 5-3. 다음 주 점검의 순서

1. 이 쇼핑몰의 열린 실행 기록 중 비교 기간이 끝난 것을 모은다.
2. 대상 광고(새 광고를 추가한 경우 새 광고 · 기존 광고 둘 다)의 지표를 기준 기간과 같은 길이 · 같은 귀속 기준으로 조회한다.
3. 결과를 먼저 판정해 출력 맨 앞(`action_reviews`)에 둔다. 함께 바뀐 조건이 있으면 효과를 분리할 수 없다고 쓴다.
4. 그 다음 새 행동을 제안한다. 지난 실행이 판단 불가면 같은 광고에 새 변경을 겹쳐 제안하지 않는다(비교가 깨짐).

### 5-4. 기존 기록 보존 · 중복 합산 · 통화 [구현 · 미리보기]

**같은 날 중복(직접 입력 ↔ Meta 하루 합계)** — 같은 쇼핑몰 · 날짜 · 채널 ‘메타’만으로는 중복으로 보지 않는다(`launchroas/adlog-core.js`).

| 판정 | 조건 | 합계 기본값 |
|---|---|---|
| 확정 중복 | 네 가지가 **모두** 일치: ① 광고계정(직접 입력에 고른 계정 = 하루 합계 계정) ② 기간(같은 하루) ③ 집계 범위(직접 입력이 ‘광고계정 하루 전체’) ④ 같은 원화 금액(1원 미만 차이) | 제외(사용자가 포함으로 바꿀 수 있음) |
| 다른 계정 | 직접 입력 계정 ≠ 하루 합계 계정, 또는 ‘다른 광고계정’으로 입력 | 중복 아님 · 포함 |
| 중복 가능 | 근거가 하나라도 없음 — 같은 계정 · 같은 금액이어도 범위를 모르면, 범위가 ‘일부 캠페인 · 광고’면, 금액이 다르면, 예전 기록이면 | **포함 · ‘선택 필요’ 표시** + 확인 안 된 근거를 표에 적고 합계 옆에 건수 · 금액 |
| 비교 안 함 | 날짜 형식이 예전 형식(예: `03.20`) · 다른 채널 | 포함 |

- 기간: 두 기록 모두 하루 단위라 날짜가 같을 때만 비교한다. 직접 입력 양식에 **광고계정(모름 / 이 쇼핑몰 연결 계정 / 다른 계정) · 집계 범위(모름 / 계정 하루 전체 / 일부 캠페인 · 광고)** 를 선택 항목으로 추가했다(새 기록부터 판정이 정확해짐).
- 사용자 선택: 표의 ‘합계에 포함 / 제외’ 선택은 `tool_records`에 `tool_type='ad_log_decision'`(`{record_id, store_id, include, decided_at}`)으로 **덧붙여** 저장하고 기록별 최신 1건을 쓴다. 다시 불러와도 유지된다. 이 종류는 운영 메인이 읽지 않아(메인은 `ad_log` · `margin_calc`만 조회) 메인 화면에 영향이 없다. `tool_records`에 `tool_type` 제약이 없음을 원격 DB에서 읽기 전용으로 확인 → **스키마 변경 불필요**.
- 기존 기록은 수정 · 삭제하지 않는다.

**통화**
- 통화 없는 기존 기록 = 원화. 근거(코드): 메인 입력칸 `index.html:881` ‘지출 (원)’ · `:882` ‘전환 매출 (원)’, 미리보기 입력칸 `launchroas/index.html:144` ‘광고비 (원)’, Meta 하루 합계는 원화 계정만 저장(`adlog-meta.js:35`). 새 직접 입력에는 `currency:'KRW'`를 명시한다.
- 외화 기록: 원본 금액 · 통화 · 기록에 저장된 적용 환율(`fx_krw_per_unit`)을 바꾸지 않고 ‘USD 48.5 × 1,400 = ₩67,900’처럼 함께 보인다. 환율이 없으면 ‘USD 기록 · 적용 환율 없음 · 합계 제외’로 표시하고 0원으로 넣지 않는다.

**변경 → 결과 연결**: 결과 기록은 `action_id`로 변경 기록을 가리키고 측정 시각순으로 모두 보존(가장 늦은 것이 현재 결과). 변경 기록이 지워지면 결과는 ‘연결된 변경 기록 없음’으로 남는다. 쇼핑몰 삭제 트리거는 `meta_auto`만 지우므로 변경 · 결과 기록은 ‘삭제된 쇼핑몰 기록’으로 남는다(직접 입력과 같은 처리).

### 5-5. 소재 저장 — Storage 없이 시작하는 최소 방식

**1단계(추가 Storage 없음 · 제안 기본값)** — 변경 기록 JSON 안에 텍스트로 저장한다.

| 저장 | 내용 | 이미 받는 값인가 |
|---|---|---|
| 지표 | 기준 기간 값 + 측정 상태(측정 · 미측정 · 조회 실패) + 기간 · 귀속 설정 · 통화 | 예(주간 점검 스냅샷) |
| 문구 | 본문 · 제목 · 버튼 · 형식(이미지 · 영상 · 캐러셀 · 동적) · 게재 위치 요약 | 예 |
| 소재 ID | 광고 ID · 크리에이티브 ID · 영상 ID, 이미지 해시(`image_hash` 필드 추가 필요) | 광고 · 영상 ID는 받음. 크리에이티브 ID · 이미지 해시는 조회 필드 추가 필요 |
| 확인 날짜 | 소재 정보를 조회한 시각 | 예 |
| 이미지 참조 | Meta가 준 이미지 · 썸네일 주소(만료 가능 표시) | 예 |

이 방식으로 가능한 것: 무엇을 바꿨는지(문구 전/후는 텍스트로 정확히 비교), 같은 광고의 소재가 바뀌었는지(크리에이티브 ID · 이미지 해시 · 영상 ID 비교), 결과 판정에 쓴 기준값의 재현.

한계(화면 · 결과에 표시):
- 이미지 주소는 서명된 CDN 주소라 시간이 지나면 열리지 않는다(만료 시점 미확인). 이미지가 사라지면 **변경 전 이미지를 눈으로 다시 볼 수 없다** — 문구 · ID로만 비교한다.
- 광고주가 Meta에서 소재를 바꿔도 크리에이티브 ID가 바뀌는지는 **미확인**(실측 필요). ID가 같으면 이미지 해시로 보조 확인하고, 둘 다 없으면 “소재 변경 여부 확인 불가”로 둔다.
- 이미지 내용(구도 · 이미지 속 글자)의 전/후 비교는 이 방식으로 불가. 사용자가 변경 내용 칸에 적은 설명만 남는다.
- 영상은 ID만 남고 장면 비교는 불가(현재도 영상 장면은 분석하지 않음).

**2단계(실제 이미지 보관 — 꼭 필요할 때만)**: 아래 중 하나가 실제로 필요해질 때만 검토한다.
- 사용자가 “변경 전 이미지”를 결과 화면에서 다시 봐야 판단할 수 있다는 요구가 확인될 때
- 이미지 속 글자 · 구도를 바꾼 테스트가 많아져 텍스트 설명으로는 결과 근거가 남지 않을 때

방식: 변경 기록을 저장할 때 해당 광고의 썸네일 1장만(최대 800px) Supabase Storage 비공개 버킷에 사용자별 경로로 저장, 변경 기록이 지워지면 함께 삭제. 검토 항목: 용량 · 비용(무료 플랜 저장 한도 내인지), 광고 이미지 권리(사용자 자신의 광고 소재만), 보관 기간.

### 5-6. 운영 메인 호환 — 먼저 배포해야 하는 이유와 최소 변경안 [준비 · 미배포]

**의존 관계(코드 · 데이터)**
1. 미리보기(`launchroas/adlog.js`)와 운영 메인(`tools.js` `renderAdlog`)은 같은 Supabase 표 `tool_records`의 `tool_type='ad_log'` 행을 사용자별로 모두 읽는다. 미리보기에서 저장한 변경 · 결과 기록은 곧바로 운영 메인에도 나온다.
2. 운영 메인(master)의 광고비 칸은 `'₩' + Math.round(r.spend)` — 금액 없는 기록은 **‘₩NaN’**. 테스트를 기존 `tools.js`로 돌려 실제로 확인했다. 합계는 `Number(r.spend) || 0`이라 부풀지 않지만 변경 기록이 성과 기록처럼 보인다.
3. 운영 메인은 master에서 `scripts/build-static-output.js`가 `index.html`의 `<script src>` 목록대로 복사해 배포된다.
4. 2026-10-06 운영 DB 집계(읽기 전용): `ad_log` 전체 0건 → 지금은 영향받는 화면이 없고, 순서 문제는 변경 기록 저장을 켤 때 생긴다.

**최소 변경안(운영 메인)** — `tools.js` 5줄 추가 · 2줄 변경, 새 파일 없음
- `source`가 `change` · `change_result`인 기록: 합계 제외, 광고비 칸 ‘—’, ‘변경 기록 · 합계 제외’ / ‘결과 기록 · 합계 제외’ 태그. 광고비가 숫자가 아니면 ‘—’.
- 기존 기록의 합계 · 표시는 그대로(중복 판정 · 사용자 선택은 LaunchROAS 광고 기록에서만 — 메인과 미리보기 합계가 중복 가능 기록에서 다를 수 있음).
- master와 이 브랜치의 기준 `tools.js`가 같아 그대로 적용된다. 로컬 브랜치 `compat/main-adlog-nan`(master 기준, 푸시 안 함)에 같은 변경 + 테스트를 커밋했다.
- 검증: `tests/open-beta-simplification.test.js` 새 테스트(₩NaN 없음 · 태그 · 기존 합계 ₩22,000 유지) 포함 65개 통과.

**운영 메인과 미리보기의 차이(최소 변경 배포 후)**

| 항목 | 운영 메인(`tools.js`, 커밋 409399f) | LaunchROAS 미리보기(`launchroas/adlog*.js`) |
|---|---|---|
| 새 기록 종류(`change` · `change_result`) | 목록에 표시 · 금액 ‘—’ · ‘변경 기록/결과 기록 · 합계 제외’ 태그 · 삭제 가능 | 목록 + ‘실행 기록 · 결과 비교’ 카드(비교 기간 · 기준값 · ①②③) |
| `ad_log_decision`(사용자 선택) | 읽지 않음(목록에도 안 나옴) | 기록별 최신 선택을 합계에 반영 |
| 같은 날 직접 입력 + Meta 하루 합계 | 둘 다 합계에 더함(지금과 같음) | 확정 중복(계정 · 기간 · 범위 · 금액 모두 일치)은 제외, 중복 가능은 포함 + ‘선택 필요’ |
| 원화가 아닌 기록 | 숫자를 그대로 원화처럼 더함(예: USD 10 → ₩10) — 지금과 같음, 현재 자동 수집은 원화만 저장 | 저장된 환율이 있을 때만 원화로 더하고, 없으면 합계 제외 표시 |
| 같은 기록 세트 검증 | 합계 ₩46,010(`tests/open-beta-simplification.test.js`) | 선택 반영 ₩24,000 · 선택 전 ₩34,000(`launchroas/adlog-core.test.js`) |

따라서 중복 가능 기록이나 외화 기록이 있으면 두 화면의 총 광고비가 다를 수 있다(운영 DB에는 현재 `ad_log` 0건). 운영 메인까지 같은 규칙을 적용하려면 메인에 선택 UI와 `ad_log_decision` 조회가 필요해 최소 변경 범위를 넘는다 — 별도 결정 사항.

**합계 일치안(별도 로컬 브랜치 `compat/main-adlog-parity`, 커밋 38feaab · 최소 수정 위에 얹음)**
- 루트에 `adlog-core.js`(미리보기 `launchroas/adlog-core.js`와 같은 내용)를 두고 `tools.js`보다 먼저 불러온다.
- `store.js`가 로그인할 때 `ad_log_decision`도 읽는다(읽기만 — 메인에는 선택 UI가 없고 쓰지 않음).
- `tools.js` 합계 = 공통 규칙(확정 중복 제외 · 중복 가능 포함 · 기록별 환율 없는 외화 제외 · 변경/결과 기록 제외 · 저장된 선택 반영). 총 광고비 아래에 ‘중복 가능 n건 포함 · 선택 필요 / 확정 중복 · 선택 제외 · 환율 없는 외화 건수’를 표시하고, 표의 중복 가능 행에는 ‘선택은 LaunchROAS 광고 기록에서’를 붙인다.
- 검증: 같은 기록 · 선택으로 미리보기 테스트와 같은 ₩24,000(선택 있음) · ₩34,000(선택 없음). 이 브랜치 전체 테스트 637개 중 634개 통과 — 실패 3개는 새로 받은 작업 폴더의 마이그레이션 파일이 CRLF여서 `
` 기준 정규식이 맞지 않는 기존 테스트(변경 파일과 무관).
- 남는 차이: 메인은 선택을 고를 수 없다(LaunchROAS에서 고른 값만 반영). 공통 파일을 고치면 루트 사본도 같이 바꿔야 한다.

**기능 스위치** — 변경 · 결과 기록 **저장**은 `window.LAUNCHROAS_FLAGS.adlogChangeRecords === true`일 때만. 운영 · 미리보기 코드 어디에도 이 값을 넣지 않았다(기본 꺼짐). 꺼져 있으면 양식은 열리지만 저장 버튼이 꺼지고 Meta 조회도 하지 않는다(테스트로 확인). 켜는 순서: ① 메인 최소 변경 master 배포 → ② 운영 메인에서 ₩NaN 없음 확인 → ③ `launchroas/index.html`에 스위치 값 추가 후 미리보기 배포.

## 6. 절감액 · 성과 비교 기준 [구현 · 미리보기 — 실제 데이터 미검증]

### 6-1. 구분과 계산 범위

| 구분 | 정의(코드: `launchroas/adlog-change-core.js`) | 성과 집계(`outcomeSummary`) |
|---|---|---|
| 실제 지출 변화 | 같은 길이 기간 · 같은 통화의 광고비 차이 | 지출 변화에만 더함 |
| 확인 가능한 변화 | 구매 수 · 구매당 광고비 · Meta 귀속 ROAS의 전후 — **이익을 계산하지 못해도 항상 표시**, 판정은 이것으로만 | 상태별 건수 |
| 광고비 차감 후 예상 이익 변화(`kind: actual`) | 이 광고의 실제 주문 상품 · 비용으로 계산할 수 있을 때만. **광고별 주문 연결(UTM 등)이 없어 현재는 해당 없음** | 검증된 이익에만 더함 |
| 연결 상품 기준 참고 계산(`kind: reference`) | `연결 상품 주문당 광고 전 잔액 × Meta 귀속 구매 수 − 광고비(원화)`. 귀속 구매가 모두 연결 상품이라는 근거가 없어 **검증된 이익이 아님** · 판정에 쓰지 않음 | **제외**(참고 건수만 셈) |
| 이익 변화 계산 보류(`kind: withheld`) | 연결 상품 마진 · 구매 측정 · 환율 중 하나라도 없음 | 제외(보류 건수만 셈) |
| 계산에서 발견한 비용 누락 | 연결 마진이 그 뒤 낮아진 경우 — 빠졌던 비용을 계산에 넣은 것 | **절약액에 합산하지 않음** |

- 모의 화면의 ‘+63,000원’은 구매 증가 3건 × 연결 상품 주문당 21,000원과 같은 값이었다 — 이 계산이 위 참고 계산이며, 실제 이익 변화로 표시하지 않도록 바꿨다.
- 쇼핑몰 전체 ‘광고비 차감 후 예상 이익’ 변화는 특정 광고의 효과로 돌리지 않는다(결과 카드에 쇼핑몰 전체 이익을 쓰지 않음).

### 6-2. 개선 성공으로 보지 않는 경우

- 광고비가 줄었지만 구매 · 매출도 함께 줄었다 → “지출 감소”로만 기록, 개선 성공 아님.
- 판정 기준(확인 가능한 지표): 개선 = 구매가 줄지 않고 구매당 광고비 10% 이상 낮아짐 / 악화 = 구매당 광고비 10% 이상 높아짐(구매가 늘고 광고비가 줄지 않은 경우 제외) 또는 광고비가 줄지 않았는데 구매 감소 / 그 밖은 차이 작음. 10%는 표시용 참고 기준이며 통계적 유의성이 아니다.
- 표본 크기는 판정 조건으로 쓰지 않는다. 전후 구매가 적으면(합계 10건 미만 — 참고 기준) “우연한 변동으로 방향이 바뀔 수 있음”을 주의로 표시한다.
- 비교 기간 길이 · 통화 · 상품 계산 범위 · 귀속 기준이 다르다 → 비교 불가.
- 함께 바뀐 조건(할인 · 예산 · 상품 · 타깃)이 있다 → 효과 분리 불가로 표시.
- 귀속 지연이 남은 기간(최근 1~3일)을 포함 → 잠정 결과로 표시.

### 6-3. 비교 조건 표시

결과마다 기간 · 통화 · 환율 · 상품 계산 범위(일부/전체) · 할인 여부 · 예산 변화 · 판매량 변화 · 계절성(행사 기간 등) · 귀속 지연 여부를 표시한다. 단순 전후 변화를 LaunchROAS의 효과라고 쓰지 않는다.

### 6-4. 향후 성과 홍보의 근거 기록

집계용으로 다음을 남긴다(개인정보 없이, `outcomeSummary`): 대상 실행 수, 상태별 건수, 실제 지출 변화 합계, 검증된 이익 변화(현재 0건), 참고 계산 · 계산 보류로 제외한 건수, 측정 기간, 비교 방식(전후 비교 · 새 광고 병행), 개선 · 악화 · 차이 작음 · 판단 불가 건수(개선되지 않은 사례 포함), 비교 불가로 빠진 건수와 이유, 데이터 누락 여부.
평균 절감액 · 효과 수치는 위 기록이 충분히 쌓이고 비교 방식이 정해지기 전에는 만들지 않는다.

## 7. 화면 · 적용 방식 · 품질 검수 [제안]

### 7-1. 대시보드 원칙

- 기본: 결론(판정) · 핵심 숫자 · 다음 행동 한 줄. 근거 · 개선안 · 실행 기록은 상세에서.
- 내부 필드명 · 코드 · 기술 설명은 화면에 쓰지 않는다(현재 `insights.js`의 한국어 변환 유지).

### 7-2. 출력 예시

> 1번은 2026-10-06 실제 저장 결과에서 옮긴 것이고, 2~4번은 **가상 사례**다.

**1. 유지 (실제 — 9월 전환광고)**
- 카드: 9월 전환광고 · 유지 / 구매 2→7건 / 광고비 +42% / ROAS 432% / 권장 행동: 현재 광고 유지 / 확인 사항: 랜딩 조회 집계 기준 확인
- 판단 근거(펼침): 클릭률 2.62%로 전주와 비슷 · 귀속에 조회 후 1일 · 참여 후 1일 포함 → 구매가 모두 클릭에서 나왔다고 볼 수 없음
- 광고 개선안(선택): 본문 첫 줄을 제품 특징으로 바꾼 새 광고를 같은 광고 세트에서 비교(운영자 검증 결과 — 화면 결과는 이전 기준이라 ‘보류’ 표시)

**2. 개선 필요 (가상)**
- 카드: 니트 가디건 광고 · 우선 확인 / 구매 9→4건 / 광고비 +5% / ROAS 210% / 권장 행동: 첫 장면 문구만 바꾼 새 광고 추가 / 확인 사항: 없음
- 판단 근거: 광고비는 비슷한데 클릭률 1.8% → 1.1%, 같은 목적 광고 중앙값 1.6%보다 낮음 · 본문 첫 줄이 할인 안내뿐
- 광고 개선안(기본 펼침): 무엇을 바꿀지 → 첫 줄을 사용자 입력 강점(“울 50%”)으로 / 바로 쓸 예시 / 비교 방법 → 같은 광고 세트에 새 광고, 광고별 클릭 수백 회 · 구매 수 건 이상 쌓인 뒤 비교

**3. 데이터 부족 (가상)**
- 카드: 신상 원피스 광고 · 판단 보류 / 신규 광고 / 광고비 3.2만원 / 구매 1건 / ROAS 미측정 / 권장 행동: 데이터를 더 쌓은 뒤 판단 / 확인 사항: 구매 3건 미만 · 표본 부족
- 개선안 없음(버튼 없음)

**4. 지표가 엇갈림 (가상)**
- 카드: 데님 팬츠 광고 · 확인 필요 / 구매 6→6건 / 광고비 −20% / ROAS 380% → 470% / 권장 행동: 할인 종료 후 한 주 더 비교 / 확인 사항: 같은 기간 할인 진행(함께 바뀐 조건)
- 판단 근거: 광고비가 줄고 ROAS가 올랐지만 할인이 함께 진행돼 광고 효과와 분리할 수 없음 → 예산 조정 제안 없음

### 7-3. MD와 사례를 서버 지시문에 연결하는 코드 [준비 · 미배포 · 기본 꺼짐]

- 파일을 저장했다고 적용된 것이 아니다. 연결 코드는 `supabase/functions/_shared/ai-policy.mjs`에 있고, 시크릿 `AI_POLICY_VERSION=policy-2026-10-06.3`을 넣고 함수를 다시 배포해야 켜진다. 지금 배포된 함수 · 시크릿은 바꾸지 않았다(기본은 기존 지시문 그대로).
- 지시문: `policySystemPrompt()`가 기존 `SYSTEM_PROMPT`에서 정책과 충돌하는 문장(고정 표본 기준 ‘노출 수천 회 · 구매 3건 미만이면 보류’, ‘유지일 때만 테스트 후보’)을 바꿔 끼우고 정책 압축본(`POLICY_ADDENDUM`)을 붙인다 — 같은 지시문에 모순을 남기지 않는다. 교체 대상 문장이 없으면 오류를 낸다(테스트로 확인). 기본(정책 꺼짐) 지시문은 그대로라 **현재 배포된 지시문에는 고정 표본 기준이 남아 있다.** 판정 ‘추가 확인’을 추가(이 판정은 변경안 · 예산 메모를 서버가 지운다). 미확인 규칙(랜딩 페이지 조회 차이 원인 · 게재 위치별 제목 노출 규칙)은 확정 기준으로 쓰지 말라고 명시한다.
- 사례: `CASES` 12개 — 관찰 10개(영상 6 · 이미지 4, 각 `evidence`가 video_frames/image, 영상은 ‘시간대별 프레임 확인 · 음성 미확인 · 프레임 사이 움직임 · 편집 미확인 · 성과 미확인’), 일반 가설 2개(`kind:'hypothesis'`). 광고마다 서버가 규칙 신호(같은 목적 광고 중앙값 대비 클릭률 · 구매율)와 소재 형식으로 **최대 2개**만 고른다. 신호가 없으면 사례를 보내지 않는다. 이미지 광고에는 영상 사례를 주지 않는다.
- 기록: 결과에 `policy_version` · `playbook_version`(꺼져 있으면 null), 광고별 `case_ids`(서버가 고른 ID). 화면은 `policy_version`이 없는 저장 결과를 ‘이전 기준 결과’로 표시한다(지금 저장된 결과가 이 상태 — 08-REAL 캡처).
- 검증: `tests/ai-policy.test.mjs` 5개(기본 꺼짐 · 관찰/가설 구분 · 사례 선택 · `<reference_cases>`는 넘길 때만 · ‘추가 확인’ 처리와 사례 ID 기록). 기존 `ai-weekly-core` 테스트 그대로 통과. Deno 타입 검사에서 `ai-weekly-review/index.ts`의 기존 오류 1건(수정 전에도 있음, 배포에는 영향 없었음)이 남아 있다.
- 토큰 · 비용(추정 · 미측정): 압축 지시문 약 +900토큰, 사례 2개 약 +500토큰 → 광고 1개 호출 입력 약 +1,400토큰(약 +$0.003). 켜기 전에 운영자 검증 경로로 같은 입력의 이전/새 기준을 비교한다(9장 비용).

## 10. 사용자 광고 영상 분석 준비 [준비 · 미배포 · 유료 호출 없음]

### 10-1. 영상 원본을 받을 수 있는가
- 주간 점검은 지금 크리에이티브의 `video_id`와 썸네일 주소만 받는다(영상 파일은 받지 않음).
- Graph API Video 레퍼런스(v26.0, 2026-10-06 원문 확인): `source` = “A URL to the raw, playable video file”. 권한 설명은 공개 영상에 페이지 · 사용자 토큰이 필요하다는 내용뿐이라, **광고 전용 영상에 지금 연결 토큰으로 `source`가 오는지는 미확인** — 실제 호출로만 확인된다.
- 확인용 함수 초안: `supabase/functions/ad-video-source/index.ts`(미배포). 본인 쇼핑몰의 연결 계정 광고만, 광고 → `video_id` → `/{video_id}?fields=source,length,picture`. 영상은 서버에 저장하지 않고 재생 주소만 요청한 사용자에게 돌려준다. Deno 타입 검사 통과.
- 대안(원본을 못 받을 때): **사용자 업로드** — 화면에서 영상 파일을 고르면 브라우저 안에서 프레임만 뽑는다(`launchroas/video-frames.js`, 화면 미연결). 영상 파일은 서버로 보내지 않는다.

### 10-2. 장면 · 프레임 · 음성을 지표와 연결하는 최소 구현
1. 프레임 계획(`planFrameTimes`): 0~3초 0.5초 간격(첫 3초 훅) + 이후 간격을 넓혀 최대 24장 + 마지막 프레임.
2. 프레임 추출: 화면에 보이는 탭에서 `<video>` 탐색 + canvas(최대 가로 512px JPEG). 숨김 탭에서는 `<video>`가 영상을 불러오지 않을 수 있다(경쟁사 조사에서 확인 — 그때는 WebCodecs 디코딩으로 우회했음).
3. 음성: Claude API는 음성 입력을 받지 않는다. 사용자가 준 자막(SRT) · 전사 텍스트가 있을 때만 넣고, 없으면 결과에 “음성 미확인”을 반드시 남긴다(출력 검증이 강제).
4. 요청: 광고 지표 · 문구 · 프레임(각 시각 표시) · 전사(선택)를 한 번에 보낸다(`buildVideoContent`). 결과는 텍스트 관찰 · 문제 · 제안만 저장하고 프레임 이미지는 버린다.

### 10-3. 영상 개선안 형식과 검증
- 출력: `observed`(시각별 장면 · 화면 글자) · `hook`(상품 첫 등장 · 첫 자막 시각) · `issues`(근거 프레임 시각 필수) · `suggestions`(**어느 시간대의 무엇을 → 어떻게 바꿀지 → 대체 자막 · 장면 예시 → 비교 방법 → 근거**) · `needs_info` · `limits`.
- 서버 검증(`validateVideoOutput`): 본 프레임 밖 시간대 제안, 근거 프레임 없는 문제, 전사 없이 음성 · 음악 언급, ‘음성 미확인’ 누락을 거른다. 확인하지 않은 상품 강점 · 혜택은 지시문으로 금지하고 `needs_info`로 묻게 한다. 일부 프레임만 보므로 움직임 · 편집 리듬은 평가하지 않는다.
- 테스트: `tests/ai-video-core.test.mjs` 4개.

### 10-4. 실제 광고 영상 1개로 검증하는 절차 (승인 후)
1. `ad-video-source` 배포 → 미리보기에서 영상 광고 1개로 호출 → `source_available` 확인(못 받으면 원인 코드 기록 후 업로드 방식으로).
2. 재생 주소 또는 업로드 파일로 프레임 추출(화면에 보이는 탭) → `node scripts/video-review-dryrun.mjs <프레임 폴더> <지표.json>`으로 요청 크기 · 토큰 · 비용 추정 확인(AI 호출 없음, 로컬 프레임으로 동작 확인함).
3. 승인 후 운영자 검증 경로로 1회 호출(월 예산 안) → 출력 검증 통과 여부 · 제안이 실제 프레임을 근거로 하는지 사람이 확인.

## 11. 영상 · 이미지 처리 비용과 저장

| 영상 길이 | 프레임 수(계획) | 프레임 크기 | 입력 토큰(추정) | 비용/회(추정) | 처리 시간(추정) |
|---|---|---|---|---|---|
| 15초 | 7 + 6 + 1 = 14장 | 512×910 | 14 × 622 + 약 3,500 ≈ 12,200 | 약 $0.05 | 프레임 추출 1~3초 + AI 15~30초 |
| 30초 | 7 + 13 + 1 = 21장 | 512×910 | 약 16,600 | 약 $0.06 | 추출 2~4초 + AI 20~40초 |
| 60~90초 | 24장(간격 확대) | 512×910 | 약 18,400 | 약 $0.06 | 추출 3~6초 + AI 20~40초 |
| 음성 전사 포함 | — | — | 전사 1분 ≈ 300~600토큰 | +$0.001 이하 | 전사 자체는 사용자 입력 기준 |

- 가정: Sonnet 5.5 $2/$10 per MTok, 이미지 토큰 ≈ 가로 × 세로 ÷ 750, 출력 약 2,500토큰. **모두 측정 전 추정값**(출력 · 생각 토큰은 effort에 따라 더 늘 수 있음 — 주간 점검 실측 medium $0.034/광고).
- 서버: 새 연산 서버 없음(프레임 추출은 사용자 브라우저, AI 호출은 기존 Edge Function 방식). 요청 본문은 프레임 24장 × 약 50KB ≈ 1.2MB(Edge Function 요청 한도는 확인 필요 — 미확인).
- 저장: **추가 Storage 없음이 기본.** 영상 파일 · 프레임 · 음성은 메모리에서만 쓰고 요청 뒤 버린다(브라우저 `URL.revokeObjectURL` · 요청 객체 해제). DB에는 텍스트 관찰 · 제안 · 본 프레임 시각 · 영상 ID · 확인 날짜만 남긴다.
- 영구 보관이 필요한 경우(예: 결과 화면에서 변경 전 장면을 다시 봐야 함)에만: Storage 비공개 버킷에 대표 프레임 3장 이하, 사용자별 경로, 30일 후 자동 삭제(예약 작업) · 실행 기록 삭제 시 함께 삭제. 원본 영상은 보관하지 않는다.
