## 0. (필수 차단 단계) 방침 확정·게시 — 이 단계 없이는 아래 어떤 단계도 진행하지 않는다

**아래 1~5번(키 설정·DB 적용·함수 배포)은 이 0단계가 끝나기 전까지 순서와 무관하게 전부 보류한다.** 폼이 기술적으로 완성돼 있어도 방침이 실제 처리 흐름을 설명하지 못하면 개인정보를 고지 없이 국외 제3자(Resend)로 보내는 것과 같다.

3. `policy-consent-core.js`의 버전 상수, 기존 회원 재동의 흐름, `submit_setup_inquiry` 등 다른 마이그레이션의 버전 표기, 관련 테스트(`tests/privacy-version-consistency.test.js` 등)를 새 버전에 맞춰 함께 갱신한다.

이 0단계가 끝나기 전에는 아래 3번(마이그레이션 적용)과 5번(함수 배포)을 실행하지 않는다. 1번(Resend 계정 준비)은 순서상 먼저 해도 무방하지만, **실제로 폼이 동작하게 만드는 3·5번은 0단계 완료 후로 미룬다.**

## 발송 실패·재시도·중복 발송 처리 (2026-09-23, 두 차례 재설계)

- **시도 대 성공 분리**: Resend 호출 전에는 "시도" 카운터만 늘고(이메일당 8·카테고리별 80, 일시 장애로 인한 재시도를 흡수하기 위해 넉넉히 둠), 사용자에게 의미 있는 "오늘 문의 가능 횟수"는 이메일당 3·카테고리별 30이다. 따라서 메일 발송이 실패해도 정상 사용자는 같은 날 다시 시도할 수 있다.
- **429 두 가지 구분**: 성공 횟수를 다 쓴 경우(`QUOTA_REACHED`)는 "오늘 문의 가능 횟수를 모두 사용했어요"로, 시도 자체가 너무 많은 경우(`ATTEMPT_LIMIT`, 반복된 실패 등)는 "지금은 문의를 보낼 수 없어요"로 서로 다르게 안내한다(`contact.js`).
- **성공 상한은 Resend 호출 *전에* 예약한다(2차 재설계)**: 1차 설계는 성공 카운터를 Resend 호출 *이후*에 늘렸는데, 이러면 상한 근처에서 동시에 들어온 두 요청이 모두 "아직 여유 있음"을 보고 통과해 상한을 넘겨 발송할 수 있었다. 지금은 `claim_contact_inquiry_attempt`가 Resend를 부르기 전에 성공 슬롯을 원자적으로 확인+예약하고, Resend가 실패하면 `release_contact_inquiry_reservation`으로 되돌린다. 아래 "실제로 보장되는 것" 참고.
- **중복 발송 방지 — 두 겹**:
  1. 클라이언트는 문의 하나당 임의 식별자(idempotencyKey)를 만들어, **입력을 바꾸지 않은** 재시도에서만 같은 값을 재사용한다(입력을 고쳐 다시 제출하면 새 식별자 — 아래 참고). 서버는 Resend를 부르기 전에 이 식별자와 문의 내용 해시 조합으로 "이미 성공 처리된 요청인지" 사전 확인하고, 맞으면 Resend를 다시 부르지 않고 성공을 돌려준다.
  2. 이 사전 확인은 "조회 후 반영까지의 시간차" 때문에 **동시에 도착한 두 재시도까지는 막지 못할 수 있다.** 그래서 Resend API 호출 자체에도 `Idempotency-Key` 헤더(재시도 식별자 + 문의 내용 해시로 만든 값)를 실어, Resend 쪽에서 같은 키의 중복 발송을 걸러내는 것을 최종 방어선으로 둔다. 이 저장소 테스트는 "같은 key+같은 내용이면 항상 같은 Idempotency-Key를 Resend에 보낸다"까지만 확인한다 — Resend가 실제로 그 키로 중복을 걸러내는지는 Resend 쪽 동작이라 이 저장소에서 검증할 수 없다.
  - **입력 수정 후 재제출 구분**: 클라이언트는 카테고리·이메일·연락처·제목·본문을 이어붙인 값이 마지막 시도와 달라지면 새 idempotencyKey를 만든다. 서버도 독립적으로 (idempotencyKey, 내용 해시) 조합으로 판단하므로, 클라이언트가 실수로 같은 key를 재사용해도 내용이 다르면 "이미 처리됨"으로 착각해 수정 전 응답을 돌려주지 않고 실제로 새로 발송한다(그 경우 Resend에 보내는 Idempotency-Key도 자동으로 달라진다).
  - **알려진 한계**: 성공 여부를 확인하기 전에 페이지를 완전히 새로고침하고 같은 내용을 다시 제출하면, JS 상태가 초기화되며 idempotencyKey도 새로 만들어진다. Resend에 보내는 Idempotency-Key는 idempotencyKey와 내용 해시를 함께 묶어 계산하므로 이때도 새 값이 되고, (1)·(2) 둘 다 이 경우를 막지 못한다 — 드물게 실제로 중복 발송될 수 있다. 막으려면 서버에 "최근 제출 내용" 자체를 저장해 대조하는 별도 장치가 필요하며, 이번 베타 단계에서는 과도한 설계로 보고 넣지 않았다.
- **Resend 성공 후 기록 실패**: Resend가 성공을 반환한 뒤 DB 기록(idempotency)만 실패하는 경우, 사용자에게는 그대로 성공으로 응답한다(메일은 실제로 전달됐으므로) — 실패로 알리면 사용자가 재시도해 중복 메일이 갈 수 있다. 이 경우는 서버 로그로만 남는다. **성공 카운터 자체는 Resend 호출 전에 이미 예약해뒀으므로 이 기록 실패와는 무관하게 정확하다.**

## 성공 상한 — 실제로 보장되는 것과 아닌 것 (2차 재설계)

정직하게 남겨둔다:

- **보장됨**: 정상적인 요청 흐름과, 상한 근처에서 몰리는 동시 요청 모두에서 성공 상한(이메일당 3·카테고리별 30)을 넘겨 실제로 발송하지 않는다. `claim_contact_inquiry_attempt`가 Resend 호출 *전에* 원자적으로 확인+예약하기 때문이다(Postgres가 같은 행에 대한 동시 UPDATE를 행 잠금으로 직렬화 — "확인 후 나중에 기록"하던 1차 설계의 경쟁 상태가 없다). `tests/contact-inquiry.test.js`의 `[동시 요청]` 테스트로 재현·확인했다(Node 안에서의 모의 동시성이며, 실제 Postgres 동시성 검증은 아래 "미검증 사항" 참고).
- **보장 안 됨(알려진 잔여 위험)**: Edge Function 프로세스가 "예약 확정" 이후 "성공 기록 또는 실패 시 예약 해제" 어느 쪽에도 도달하지 못하고 강제 종료되는 극단적 상황(일반 예외가 아니라 크래시·강제 kill 등 — 일반 예외는 `finally`에서 잡혀 정상적으로 해제됨)은 그 슬롯 하나를 그날 하루 동안 영구히 소모한 채 남긴다. 영향 범위는 하루 최대 1건 남짓이고 UTC 자정에 자연히 복구된다.
- **더 엄격하게 보장하려면(과도한 설계로 판단해 이번엔 넣지 않음)**: 예약에 상태(`reserved`/`confirmed`)와 타임스탬프를 추가하고, 다음 요청마다 오래된 미확정 예약을 만료시켜 되찾는 TTL 로직을 넣어야 한다. 이 폼의 트래픽 규모(공개 베타, 소규모)에서는 위 잔여 위험의 영향이 작고 자연 복구되므로 지금은 넣지 않았다 — 실제 동시 트래픽이 늘거나 이 잔여 위험이 문제가 되면 추가할 것.

## 카테고리별 일일 한도와 그 한계

전역 일일 한도를 "쇼핑몰 시작 질문/사이트 이용·오류/택배·도매 제휴" 세 카테고리로 나눠, 한 카테고리가 도배돼도 다른 두 카테고리는 정상 이용자에게 계속 열려 있게 했다(가용성 개선). **다만 이것만으로 남용 방지가 끝난 건 아니다** — 이메일 형식 검증은 실제 수신 가능 여부를 확인하지 않고, IP 등 접속 신호를 이 함수/DB 계층에서 신뢰성 있게 얻을 방법을 확인하지 못해(Supabase Edge Function이 어떤 헤더로 실제 클라이언트 IP를 안정적으로 넘겨주는지 검증되지 않아 추측해서 넣지 않았다) 넣지 않았다. 즉 회원 계정을 여러 개 만들 수 있는 공격자에게는 여전히 카테고리당 하루 상한(성공 30·시도 80)까지 열려 있다(계정당 상한은 로그인 계정 기준이라 답장 주소를 바꿔도 우회되지 않는다). 계정 대량 생성이 문제가 되면 회원가입 단계(Supabase Auth 이메일 확인·CAPTCHA)에서 막는다 — `docs/contact-inquiry-privacy-draft.md` "Turnstile 제거 판단" 참고. IP 기반 제한이 필요하다고 판단되면, 실제 Supabase Edge Function 요청에서 신뢰 가능한 클라이언트 IP 헤더를 먼저 확인(공식 문서·실제 요청 로그로)한 뒤 별도로 추가할 것.

## 확인 시나리오

- 비회원/회원: 입력 → 정상 접수 → 운영자 메일 도착, 받은 메일 답장 시 사용자의 이메일 주소가 수신자로 설정되는지 확인.
- 서버 장애·메일 거절: 성공 문구 없이 입력 유지, **같은 창에서 다시 제출하면 실제로 재시도가 되는지**(발송 성공 횟수가 줄지 않았는지) 확인. 메일 앱이 없는 브라우저에서도 화면 안 접수가 작동하는지 확인.
- 중복 제출: 발송 성공 직후 네트워크를 끊어 응답을 못 받은 것처럼 재현하고 같은 창에서 다시 제출 — Resend에 두 번째 실제 호출이 나가지 않고 성공 응답만 오는지 확인(idempotencyKey 재사용).
- 입력 수정 후 재제출: 실패한 문의의 내용을 고친 뒤 다시 제출 — 고친 내용이 실제로 발송되는지(수정 전 응답이 재사용되지 않는지) 확인.
- 잘못된 이메일·짧은 문의·동의 없음·반복 제출: 실제 메일이 가지 않는지 확인.
- 로그아웃 상태로 `#/contact` 진입 시 폼 대신 로그인 안내가 보이고, 로그인 버튼이 로그인 모달을 여는지 확인. 로그아웃 상태에서 함수를 직접 호출하면 `401 LOGIN_REQUIRED`인지 확인.
- 오늘 성공 횟수를 다 쓴 이메일로 추가 제출 시 "오늘 문의 가능 횟수를 모두 사용했어요" 문구가 뜨는지 확인.
- **동시 요청(스테이징 전용, 자동화 테스트는 이미 완료)**: 같은 이메일로 거의 동시에 2개 탭에서 제출해, 상한 근처에서 실제로 몇 통이 도착하는지 확인 — 1통만 성공하고 1통은 "오늘 문의 가능 횟수를 모두 사용했어요"를 받아야 한다. 이 저장소의 자동화 테스트(`tests/contact-inquiry.test.js`)는 Node 안의 모의 동시성으로 이미 확인했지만, 실제 Postgres 엔진에서의 동시성은 검증하지 못했다(아래 "미검증 사항" 참고) — 스테이징에서 실제로 재현해 볼 것.
- 390px, 키보드 Tab/Enter, 화면 낭독기의 필드 이름과 결과 안내 확인.

공개 사이트 키가 비어 있으면 전송 버튼은 잠겨 있고 기존 이메일 주소로 직접 문의할 수 있다. 임의 키나 시험 키로 운영 사이트를 열지 않는다.
